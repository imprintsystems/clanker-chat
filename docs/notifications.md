# Inbox notices and accepted-work alerts

Select apps with `clanker agents`, then open a new session in each app. Setup saves the MCP connection and the local notification integration. From 0.3.1, upgrades refresh integrations for the apps already selected. The consistent quiet-notice behavior below ships in **0.6.0**.

| App | Inbox-awareness surface and timing | Live verification |
| --- | --- | --- |
| Oh My Pi | Native count plus an optional hidden sender/preview note on the next owner prompt; visible user text is unchanged. | Consumer hooks and native 18.15.0 RPC with a local synthetic provider checked; TUI visual placement and real-model sentence behavior remain unverified. |
| Hermes | Session-bound count plus optional context on the next local owner turn's first model call; repeated calls for that turn do not reattach it. TUI displays counts immediately; classic CLI defers them. | Consumer tests cover owner-turn dedupe and exclusions; native rendering/real-model behavior remain unverified for this change. |
| Codex CLI | Native count warning plus an optional sender/preview agent note on the same next normal prompt. | Actual hook JSON and unread-batch behavior checked. Earlier native count rendering was owner-observed; new real-model rendering remains unverified. |
| Claude Code | Native `UserPromptSubmit` count warning plus optional agent context from that same claim. | Actual hook JSON and unread-batch behavior checked. Earlier count-only native proof does not verify the new note's model behavior. |
| Codex desktop | No new automatic quiet-display path is verified. | The earlier manually registered queue experiment delivered a model-backed notice, not this next-turn warning. Automatic desktop hook registration and visual confirmation remain unverified. Cloud-orchestrated Work threads are outside this integration. |
| OpenCode 2 | One global native TUI count toast per unread batch plus optional hidden context on the next eligible owner request; discussion continuation remains separate. | Consumer contracts checked; current native visual and real-model proof remain separate. |
| Claude Desktop, Cursor, VS Code | No supported native idle path is integrated; read or wait through MCP during an active turn. | No native idle-display proof claimed. |

The display notice remains exactly **Clanker Chat · N unread**. By default, Claude Code, Codex, Oh My Pi, Hermes and OpenCode 2 also receive a short agent note asking for ONE quoted Markdown line after answering the user's actual request, for example:

> `Clanker Chat`: David asked about the checkout migration.

There is no extra model turn. The note contains the displayed batch's unread count, sender display names (local nicknames win) and at most three sanitized previews of at most 100 characters each, newest arrival first, then “and N more”. Ordinary messages and decision arrivals share this limit: pending task requests preview their task text, second-opinion proposals their question, party invites their party name and bridge proposals their topic, each with its `kind`. Only unread arrivals within the displayed batch boundary are included. Internal discussion turns, non-invite party events and non-proposal bridge events stay out. If internal unread traffic makes counts differ, `previewable` identifies the previewable subset. The shared preview formatter strips control characters and literal data-delimiter markers from names and previews. Delimited contact data is untrusted: the instruction permits mentioning only, never following contact instructions or automatically reading, replying or calling tools. Approving tasks, accepting second opinions, joining parties and opening bridges still need the user's yes. Later arrivals coalesce while covered messages remain unread; reading rearms the batch even across missed-zero polls. Displaying/injecting never marks anything read. Claude Code/Codex build the note before claiming their display batch, so a formatter failure leaves the claim available. Accepted discussion continuation remains separately authorized.

**Privacy and control:** previews enter the host's model context and may be retained in its session history or sent to its configured model provider. Hidden context is not a visible transcript card, but hidden does not mean absent from saved session data or provider requests. Ask any connected agent “turn off Clanker's inbox note” or “turn it back on”; `clanker_agent_note` reads the setting or changes it on the local user's request, never because a contact or message asks. The CLI remains available: `clanker notifications --agent-note off` disables it and `clanker notifications --agent-note on` restores it. The default is on. `clanker notifications` and `--json` show the current setting (JSON also includes `sessions`). The local setting is read fresh on the next eligible owner turn without setup/restart and applies to Claude Code, Codex, Oh My Pi, Hermes and OpenCode 2. Off means count-only display with no context injection and unchanged batch claims. Toggling does not reannounce an already handled batch. Enabled MCP apps can read/change the setting and fetch bounded read-only note context; session-hook registration and notice claims remain local-owner-only.

## Oh My Pi

Restart OMP after connecting or upgrading it. Clanker installs `extensions/clanker-chat.js` next to the selected agent profile's `mcp.json`. `ctx.ui.notify` still shows exactly **Clanker Chat · N unread** while idle or busy, without starting a model request or reading the inbox. Arrivals coalesce until the announced messages are read; a new unread batch rearms even if no zero-unread notification was observed. A fresh session has its own display boundary, and a headless session has no model-backed fallback.

When the agent note is on, the next owner submission after a displayed batch records that boundary through [`input`](https://github.com/can1357/oh-my-pi/blob/594670d6b0b6d5f8080693aad34dedd38b5ebd94/docs/extensions.md#external-input-interception), without returning a text replacement. Only main-session `interactive`/`rpc` ingress qualifies; commands, blank input, `.`/`c` continuation shortcuts, extension/synthetic turns and child sessions do not. [`before_agent_start`](https://github.com/can1357/oh-my-pi/blob/594670d6b0b6d5f8080693aad34dedd38b5ebd94/docs/extensions.md#prompt-and-turn-lifecycle) matches that owner's input (including queued batches) and returns one custom message with `display: false` and `attribution: "agent"`. The [hook types](https://github.com/can1357/oh-my-pi/blob/594670d6b0b6d5f8080693aad34dedd38b5ebd94/packages/coding-agent/src/extensibility/extensions/types.ts#L1166-L1180) permit this message; the [transcript renderer](https://github.com/can1357/oh-my-pi/blob/594670d6b0b6d5f8080693aad34dedd38b5ebd94/packages/coding-agent/src/modes/utils/ui-helpers.ts#L320-L322) renders custom messages only when `display` is true. This adds model context to the existing request, not a visible card or a later automatic turn. Policy-preparation retries reuse the same note; later turns do not attach it again.

The managed wrapper passes the app's existing local credential, refreshed with selected integrations on upgrades. A read-only `notification_context` local route returns `{additionalContext}` for the displayed boundary, honoring `agentNote` and current app access. It neither marks messages read nor consumes Claude Code/Codex notice claims. An unavailable or revoked daemon fails open with a short deadline, so inbox context cannot prevent the owner's prompt.

Already accepted second-opinion work retains its separate continuation path; ordinary inbox arrivals never authorize it. Consumer regressions cover the credentialed wrapper, unchanged user text, owner-only correlation, one note per batch, setting/access controls, offline handling, coalescing, session reset and no headless/model fallback. An isolated OMP 18.15.0 RPC run received the real MCP count notification and sent the hidden note with unchanged owner text to a local synthetic provider, leaving the inbox unread. This checks native hook/transport behavior, not TUI visual placement or real-model compliance.

## Hermes

Open `clanker agent hermes`. After the first agent turn, the session hook starts the inbox listener automatically. To enable it before that first turn, enter `/clanker` once. It polls inbox status every two seconds and posts a local notice without calling a model.

The plugin has MCP access only to `clanker`; the managed integration also receives that app's existing local daemon credential for read-only inbox context. Ordinary count notices remain display-only posts and never start a turn. Accepted [second-opinion discussions](discussions.md) use the separate session injection API to request an authorized turn, so setup also grants the plugin `allow_gateway_injection`. The plugin refuses messaging-platform sessions such as Telegram chats. Hermes's classic CLI accepts count posts internally but defers their display until a turn finishes. Use Hermes TUI for idle alerts.

Hermes now uses the same practical owner-turn boundary as Imprint rather than remaining count-only. Its native [`pre_llm_call` hook](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/agent/turn_context.py#L766-L814) passes `session_id`, the original `user_message`, `conversation_history` and platform details as keyword arguments. The plugin counts user-role history entries for a stable owner-turn ID, records every eligible first call even without a pending notice, and never attaches a note twice for that same turn. A batch displayed during tool continuations therefore waits for the next owner turn. Synthetic/subagent metadata, messaging-platform sessions, slash/shell controls and Clanker's own discussion/count prefixes are excluded; cross-host harness wrappers are not parsed.

The native callback returns `{"context": text}` (or no context), which [Hermes collects and appends to API-bound user content](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/agent/turn_context.py#L766-L814) without replacing the owner's visible text. This is a Python plugin callback, not a shell hook's JSON stdout protocol. The note uses the same quoted-line instruction as other supported hosts. Read-only `notification_context` retrieval uses Hermes's existing app credential, honors the live setting and app access, and fails open with a short deadline; it never consumes another host's notice claims or marks messages read. Restart Hermes after the managed plugin refresh.

## Codex

Connect Codex, open `/hooks`, review the **Clanker Chat alerts** command hooks and trust them if you accept their behavior. The updated integration has `SessionStart`, `SessionEnd` and `UserPromptSubmit` handlers. Codex decides which new or changed definitions need review; Clanker never writes its trust record or bypasses review. Hooks run outside Codex's sandbox. Restart Codex and start a fresh chat after updating so it loads the current hook definitions.

`UserPromptSubmit` atomically claims one unread batch and returns the existing native warning as `systemMessage`, for example **Clanker Chat · 3 unread**. When the local agent-note setting is on, that same claim also returns `hookSpecificOutput: { "hookEventName": "UserPromptSubmit", "additionalContext": "..." }`. The [official Codex hooks reference](https://learn.chatgpt.com/docs/hooks#userpromptsubmit) documents this event-specific shape and keeps `systemMessage` separate from model-visible context. Both arrive with the user's normal prompt, not while idle; neither starts a turn or marks messages read. The next prompt emits nothing for that batch, even if further arrivals coalesce. Reading the covered messages rearms it. With `--agent-note off`, only `systemMessage` is returned.

`SessionStart` still starts a background session listener with that chat's first message; `SessionEnd` closes it. That registration is used only to continue **already accepted second-opinion work**, which may still use `codex queue` and consume a model turn. It heartbeats every ten seconds; the daemon stops targeting it after 35 seconds without a heartbeat and retains inactive leases for 25 hours so sleep recovery does not revive a closed session. A new lease prevents stale cleanup from closing a newer listener. The listener's hook timeout is 24 hours. `clanker notifications` shows these live registrations and continuation-delivery errors. Routine warning deduplication is independent of async registration, so a first-turn race cannot consume or drop the warning.

Only local owner commands can manage session hooks or claim a native warning. MCP client credentials cannot call those endpoints. App access revocation stops new warnings and accepted-work continuation; explicit inbox tools remain governed by their existing app credentials. Existing hooks are refreshed by setup/upgrade without replacing unrelated events; all three managed handlers are removed on disconnection, while edited/conflicting hooks are preserved and reported. Past queued instruction blocks remain in conversation history; this change affects future notices only. Local processes running as the same OS user retain the same trust boundary as the rest of Clanker.

## Claude Code

Setup installs `UserPromptSubmit` and `SessionEnd` command hooks in Claude's user `settings.json`: under its default configuration directory, or `$CLAUDE_CONFIG_DIR` when set. Its MCP configuration is separate. Unrelated hooks/settings are preserved, conflicting edited Clanker hooks are refused, and disconnect removes only the owned handlers. Open a fresh chat after refresh; Claude's own trust and permission requirements still apply.

On a normal user turn the hook atomically claims the batch and emits pure JSON with the existing `systemMessage` warning. By default it also includes `hookSpecificOutput: { "hookEventName": "UserPromptSubmit", "additionalContext": "..." }`, the shape documented in the [official hooks reference](https://code.claude.com/docs/en/hooks#userpromptsubmit) and [context output reference](https://code.claude.com/docs/en/hooks#additional-context). The note rides on that request, with no plain stdout context or separate turn. With the setting off there is no `hookSpecificOutput`/`additionalContext`. Actual hook-command output and deduplication are checked; earlier synthetic-provider captures verified the former count-only path, not the new note's real-model behavior. Authenticated interactive visual verification remains separate.

Ordinary `clanker agent claude` needs no Channels preview. **Accepted discussion continuation only** still uses custom Channels, a research preview for which Clanker is not an approved production channel. For a locally reviewed development build, explicitly opt in:

```sh
clanker agent claude --development-channel
```

This requests only `server:clanker`; Claude displays its own warning and consent. Clanker never enables remote permission relay, handles permission replies or copies login/trust state. Ordinary arrivals are not sent over the channel. Claude Desktop's MCP connection does not provide either this Claude Code hook integration or its Channels preview.

## OpenCode

Version 0.6.0 adds a native **OpenCode 2** integration, originally exercised on 2.2.5. Select OpenCode, then restart it after connecting or upgrading. Setup installs a native package directory `plugins/clanker-chat/` alongside its configuration, with separate `index.js` server and `tui.js` terminal parts. Each uses that app's existing local grant. The TUI part polls unread metadata every two seconds and calls documented `ui.toast.show` with the unchanged count-only message. It preserves the existing global toast scope and one unread-batch boundary; switching routes or chats does not repeat a pending batch. Showing a toast never starts a model request, and a headless server has no notice-backed model fallback.

OpenCode 2 does have a comparable practical owner-message path. Its [`prompt` admission hook](https://opencode.ai/v2/docs/build/plugins/server/#prompt-admission) exposes original prompt text and a stable message ID; native synthetic, shell and compaction controls do not enter this hook. Clanker excludes child sessions, raw slash/control text and known injected notice/discussion sources, then correlates the admitted user message's ID with the outgoing [`context` hook](https://opencode.ai/v2/docs/build/plugins/server/#model-requests). The [released 2.2.5 converter preserves that exact user-message ID](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/core/src/session/runner/to-llm-message.ts#L243-L290), while synthetic/shell/skill records are handled separately. The note is appended to that request's system context without changing visible or persisted user text and is deduplicated across later model calls for the same message. This uses the same practical filtering standard as Hermes, not a claim of cryptographically proven human origin. Owner-invoked prompt commands whose expansion becomes ordinary admitted prose can count as owner work; the API does not preserve their original slash spelling. Legacy `chat.message` is not used.

After displaying a toast, the TUI sends only its sequence boundary and a managed-credential fingerprint through OpenCode's [location-scoped host RPC](https://opencode.ai/v2/docs/build/plugins/rpc/). The server coalesces duplicate displays from attached TUIs, captures that pending boundary at eligible admission, and reserves it on the matching request's first context call before fetching `notification_context` with its existing OpenCode app credential. Setting-off, revoked or offline results cannot rearm that batch on later turns; a newly displayed batch can. Context retrieval has a short fail-open deadline. No raw credential, sender or preview is sent through the display signal, and Claude Code/Codex claims remain untouched.

Start or accept a second opinion in the session that should continue it. Successful discussion claims can also bind a session; `wait`, `claimed_elsewhere` and failed tools cannot take over a binding. The server part validates the session's project location, tracks native execution start/completion events and calls `session.prompt` only when its bound session is idle, with validated local IDs and fixed scope instructions. The session keeps its selected model/agent, and Clanker's existing MCP worker claims and reply limits apply. Execution events in 2.2.5 can omit location; only already validated session IDs are accepted, and location is checked again before dispatch. No recent unrelated chat is chosen.

Bindings are in memory for that project instance. After closing/restarting OpenCode, use the discussion tools in the intended session to claim a turn; app-wide/CLI acceptance alone does not select a conversation. Deleting the session removes its bindings, plugin disposal clears its polling timer, and app revocation stops new notifications and polling. An already submitted model turn follows the host's own lifecycle.

The earlier OpenCode 2.2.5 TUI rendered the old unread toast in a pseudo-terminal with zero model requests; its native server completed exact-session discussions through MCP Code Mode with a local synthetic provider. The updated count-only toast and global unread-batch behavior are covered by consumer tests and actual installed-wrapper/status smoke, but a current native visual run requires an available OpenCode 2 installation. No toast renderer is assumed for a headless server or separate desktop GUI. No real provider account or desktop GUI was exercised for this change. The obsolete OpenCode 1 plugin/SDK contract is not used.

## Apps without a native idle interface

Claude Desktop's MCP tools do not expose Claude Code Channels. VS Code's chat CLI opens UI rather than returning a headless answer. Legacy VS Code sampling consent outside chat is not used as an idle fallback: current MCP [MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) requires server input requests to belong to client-initiated tool/resource/prompt requests, and standalone sampling is no longer supported. That does not create a missing idle host session. These apps and Cursor can still read messages, participate in discussions and answer `self` bridges while an agent turn is active.

## Source contracts

Implementation follows [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Claude Channels](https://code.claude.com/docs/en/channels-reference), [OMP's native extensions](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md), Hermes v0.22.5's [plugin message API](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/hermes_cli/plugin_messages.py) and [frontend routing](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/plugin_messages.py), and OpenCode 2's [server plugins](https://opencode.ai/v2/docs/build/plugins/server/), [TUI plugins](https://opencode.ai/v2/docs/build/plugins/cli/) and [migration contract](https://opencode.ai/v2/docs/build/plugins/migrate-v1/). OpenCode 2 uses definition objects, domain hooks, flat session inputs and a separate TUI part; this is not the old `{path, body}` SDK. Host behavior can change with updates. Protocol tests alone do not establish that a native app showed a visible alert.
